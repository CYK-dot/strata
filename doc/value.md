# strata · 价值论证

> 状态：v1.1 ｜ 2026-11-14 ｜ 与当前实现一致
>
> 本文回答“为什么值得做”；目标见 [goals.md](goals.md)，行为契约见 [spec.md](spec.md)。

---

## 1. 论点

strata 要解决的不是“配置项没人管”，而是两件事：

1. 构建与代码直接读配置项，配置的词汇渗进了本该与它无关的地方；
2. 层与层之间没有推导边，上层必须重推下层已经知道的事实。

它交付的是一条写下来的推导：配置项 → feature，以及 feature → feature 的声明式 DAG。推导只写一次，因此可以评审、解释、测试。

---

## 2. 两个具体的错

### 2.1 判据是配置层的

```c
#if defined(MCU_HAS_PIOC) || defined(BOARD_HAS_BLE_MODULE) || defined(BOARD_HAS_AT_ADAPTER)
    tunnel_start(2);
#endif
```

这段代码三层错，层层更贵：

1. **判据是配置层的**：解域代码去读配置项本身。
2. **结论是隐式的**：“有 PIOC 或蓝牙模组就够”是一条领域结论，躺在预处理表达式里，没有名字，没有被评审过。
3. **判定是分散的**：同一条结论在 N 个使用点复制 N 次，任意一处漂移都不会被发现。

第三点最贵：它是“知道”与“以为知道”的区别。

### 2.2 同一套事实在两层各写一遍

demo 里 `bsp` 已经知道 backend 是 ble / plb / uart；`ctl` 仍要重新读 `board.has_ble_module`、`chip.pioc`、`board.has_uart_ble_adapter`，才能判断 tunnel 是否可用、能开几路。

架构上 `ctl` 依赖 `bsp`；推导上两者却是平铺的兄弟。DAG 把这条边写进契约：`bsp` 暴露 `HAS_WIRELESS_TUNNEL` / `MAX_SESSIONS`，`ctl` 只组合它们。chip/board 的词汇停在下层。

---

## 3. 为什么这不是配置管理问题

Kconfig 完全能写出等价物：

```
config SUPPORT_WIRELESS_TUNNEL
    def_bool y if MCU_HAS_PIOC || BOARD_HAS_BLE_MODULE
```

它甚至提供 `IS_ENABLED()`。差别不在“能不能推导”，而在三件事：

| 维度 | Kconfig | strata |
| --- | --- | --- |
| 语义 | 符号是选项 | feature 是软件对能力的命名 |
| 归属 | 平坦命名空间，谁引用谁都合法 | feature 有 owner，推导方向由 `requires` 声明；清单记 `by` / `from` |
| 产出 | 生成头文件 | 同时生成 CMake 视图与 C 视图，两侧同源 |

Kconfig 里没有任何东西阻止下一个人在驱动里写 `IS_ENABLED(CONFIG_MCU_HAS_PIOC)`。strata 也不阻止直接读配置项——**它只是让“谁读了配置项”变成可报告的事实**。这是刻意的：工具不替项目做配置治理。

但 feature → feature 的读取不同：它必须落在 `requires` 声明的方向内，越界是硬错误。这不是权限系统，而是求值顺序的前提；否则“谁先算”没有定义。

## 4. 价值落在四处

**4.1 知识外部化（最贵的一处）**

“哪些目标能提供这项能力”从一群人的记忆，变成一条可评审、可测试、可引用的推导。缺陷可以从“某台设备上不工作”追溯到“推导缺了一条”，而不是翻遍所有 `#if`。

**4.2 变化率解耦**

配置（芯片、板卡、产品档位）变化快、来源不可控；软件能力变化慢、可规划。焊在一起，等于让慢变的一侧持续承担快变一侧的成本。分层是依赖倒置在配置空间的版本。

**4.3 组织边界对齐**

产品用配置说话，软件用 feature 说话。把推导交给懂两侧交界的人维护，团队分工才在技术上有了落点。

**4.4 方向可评审**

`requires` 是 TOML 里的一张有向图：环在求值前报出，求值顺序确定、可复现；上层读下层 feature 不需要头文件，也不需要链接边。这是“架构树”第一次真正出现在推导层。

---

## 5. 薄弱点

**5.1 能力的跨目标同义性**

`SUPPORT_WIRELESS_TUNNEL` 在所有目标上必须同义。若不同，所谓稳定词汇只是皮肤，分支会以 `if (board == ...)` 的形式长回来。做不到同义，就说明抽象层次选错了，应下沉到承诺更少的能力。

**5.2 布尔化会失真**

有 BLE 或 PLB 就够吗？够几路？带类型的 feature（`MAX_TUNNEL_SESSIONS = 1`）能承载量，但数值一旦被重新命名为配置项本身（`PLB_UNIT_COUNT`），分层等于没做。数值必须重新命名为解域语义。

**5.3 分层是有成本的**

只有一个构建、一个开关时，`#ifdef` 更便宜。收益只在“配置数 × 使用点数”变大后出现。不写明适用边界，就会沦为“为架构而架构”。

**5.4 requires 必须完整**

声明的图必须覆盖真实的读。Python 的分支和动态读取无法在加载时可靠地静态推演，所以未执行分支里的越界读可能延迟暴露（规格 R16）。这不是免费的：契约和代码要一起维护。

---

## 6. 可证伪的检验

- **T1 零改动加产品**：新增一款产品只加一个 preset，`CMakeLists.txt` 与源码不动。
- **T2 可解释**：对任一 feature，能说出它由哪些配置项（`by`）与哪些 feature（`from`）得出，并能沿链走到底。
- **T3 失败前置**：未知项、类型不符、越界、缺失必填、重名、孤儿、环、跨组件 feature 级依赖、cone 外读取，都在求值前或读取时失败，并指向文件与行。
- **T4 确定性**：相同输入两次生成，产物逐字节一致；声明顺序不影响结果。
- **T5 多步推导**：同一套事实只写一次；上层只组合下层暴露的能力。

任何一条不成立，strata 就退化成一个更麻烦的宏表。

---

## 7. 边界

- 建**两个词汇 + 一条声明式推导 DAG**，不建配置中心。
- 必须对两侧输出，否则构建期裁剪与代码期分支会再次分家。
- 核心交付物是**推导的可评审性与可追溯性**，不是配置文件的语法。
- `requires` 只定方向，不做可见性；所有 feature 仍然全局生成、全局可读。
- 不做 per-module header，不做 config 归属，不做惰性求值，不做跨组件的 feature 级边。
- 不拒绝直接读 config，但要可见；越界 feature 读是硬错误。
