# strata · 目标定义

> 状态：v1.1 ｜ 2026-11-14 ｜ 与当前实现一致
>
> 价值论证见 [value.md](value.md)，行为契约见 [spec.md](spec.md)。

---

## 1. 一句话

strata 把**配置项**转换成带名字、带类型的 **feature**，并允许 feature 按声明的方向由其他 feature 推导；构建系统与 C/C++ 代码只读 feature。

这句话压着三个主张：

- **配置项与 feature 是两个词汇**：前者描述目标或产品（`chip.pioc`、`tier.pro`），后者描述软件能做什么（`ctl.SUPPORT_WIRELESS_TUNNEL`）。
- **两层推导，方向显式**：配置项 → feature；feature → feature 只沿 `requires` 声明的方向。求值有确定的拓扑序，环在求值前失败。
- **结果被两侧共享**：构建与代码读同一次生成的同一批值，构建期裁剪与编译期分支不会分家。

---

## 2. 它解决的问题

配置项多起来之后，让两侧直接读它们的代价：

| 现象 | 后果 |
| --- | --- |
| 判断条件直接写配置项 | 谓词随配置项数量与组合膨胀，同一条决定被复制到多个使用点 |
| 代码说配置的词汇 | 新增一颗芯片、一个档位，就要改那些本不该认识这些词的代码 |
| 构建与源码各判各的 | 没有任何东西保证两边一致 |
| 没有出处 | 没人答得上“这次构建为什么开着它”，除非把两边都读一遍 |
| 同一套事实在多层重复推导 | 上层不知道下层已经算过什么，知识在每一层复制一份，漂移无法发现 |

strata 把这条推导抽成独立的一层，只写一次、只放一处，于是它可以被评审、被解释、被测试。

---

## 3. 定位

**主战场**：承诺“不关心取值来自哪里”的那一层——控制面、协议栈、应用逻辑、命令行。

**次要场景**：底层模块里那些互相约束、手工维护易错的宏。那里 strata 只买到“求解与校验”，买不到“隔离”。

**它不是**：配置管理器、Kconfig 替代品、构建系统、运行时开关服务、强制机制、硬件专属工具。

---

## 4. 目标

- **G1 多步推导**：resolver 的入参是 `config` 与可选的 `features` 视图；feature 可以读声明方向下方的 feature。组件图与组件内 feature 图都必须无环，环在求值前失败。
- **G2 全局命名空间**：feature 全局唯一、全局可见；`requires` 只声明先后方向，不做访问控制。
- **G3 双端同源**：一次运行产出 CMake 文件与 C 头文件，不可能不一致。
- **G4 带类型**：`bool` / `int` / `float` / `string`，类型以声明为准，运行时校验返回值。
- **G5 可追溯**：清单记录每个 feature 的归属组件、实际读到的配置项（`by`）与实际读到的 feature（`from`）。
- **G6 失败前置**：未知项、类型不符、越界、缺失必填、重名、孤儿、组件/feature 环、跨组件 feature 级依赖、cone 外读取，都在求值前或读取时硬失败。
- **G7 低侵入**：五个 CMake 函数；产品由 `-DSTRATA_PRESET=<名称>` 选择，`CMakeLists.txt` 里不出现产品名。
- **G8 不治理**：不强制分层、不拦截 config 读取；feature 读只按声明的 DAG 校验，越界是错误，不是权限系统。`strata scan` 尚待实现。

---

## 5. 非目标

- 不做配置管理：值的来源、存储、分发不归它。
- 不做包管理：交给 vcpkg / Conan。
- 不做运行时开关：只管构建期与编译期的决策。
- 不替代 CMake：它是上游，产出 CMake 消费的输入。
- 不做通用建模语言：resolver 是普通 Python，不是 DSL。
- 本版只服务 CMake。
- 不做 feature 可见性 / per-module header / config 归属。
- 不做惰性求值，不做 `requires` 的自动推断。
- 不做跨组件的 feature 级边；跨组件方向只由顶层 `requires` 声明。

---

## 6. 成功判据

- **T1 零改动加产品**：新增一款产品只加一个 preset 文件，`CMakeLists.txt` 与源码不动。
- **T2 失败前置**：任何非法配置在 configure 阶段失败，并指向具体文件与行。
- **T3 可解释**：对任一 feature，能说出它由哪些配置项（`by`）与哪些 feature（`from`）得出，并能沿链走到底。
- **T4 确定性**：相同输入两次生成，产物逐字节一致；组件路径声明顺序、TOML 条目顺序不影响结果。
- **T5 一份构建文件覆盖所有产品**：切换产品只改配置命令。
- **T6 可见性可报告**（待实现）：能列出谁直接读了配置项、谁读了别组件的 feature。
- **T7 声明图前置**：组件环、feature 环、跨组件 feature 级依赖都在求值前报出。

## 7. 术语

| 术语 | 定义 |
| --- | --- |
| 配置声明（schema） | 配置项的全局词汇表：id、类型、范围、默认值、说明 |
| 配置项（item） | 声明出来的一条值，含义属于拥有它的那个领域 |
| 预设（preset） | 一份完整的配置项取值，代表一款产品 |
| 组件（component） | 一个目录：`strata_features.toml` 是契约，`strata_features.py` 是求解函数；身份由 TOML 顶层的 `component` 声明 |
| feature | 由配置项或下层 feature 推导出的带名字带类型的值，构建与代码都能读 |
| `requires` | 组件级或 feature 级的先后声明；只定方向，不做可见性 |
| cone | 组件 A 的 `requires` 传递闭包；A 的 feature 可读其中所有组件的 feature |
| resolver | 算出一个 feature 的函数，签名 `(config)` 或 `(config, features)` |
| config 对象 | 传给 resolver 的配置视图，每次读取都被记录（`by`） |
| features 视图 | 传给两参 resolver 的只读视图，每次读取都被记录（`from`） |
| 视图（views） | 生成物：一份 CMake 文件、一个 C 头文件、一份清单 |
| 清单（manifest） | 值、归属、`by`、`from`、输入哈希 |
| 逃生舱 | 全部配置项的导出（`STRATA_CONFIG_*`），刻意提供、刻意不推荐 |

## 8. 与相邻工具

| 相邻物 | 关系 |
| --- | --- |
| Kconfig | 不说明符号对软件意味着什么；strata 的主题是声明式推导图与双端视图 |
| CMake `option()` / presets | 下游消费者，不是竞争者 |
| 编译期宏 | 下游实现手段 |
| 包管理器 | 正交 |
| 运行时 feature flag | 不同问题域：那是运行期 |

## 10. 后续方向

1. **`strata scan`**：没有分层之后，这是仅剩的软约束；同时可以报告 `from` 与声明图的差异。
2. **增量与拆分**：让改一个 feature 不必重编所有订阅者；这是构建优化，不是可见性规则。
3. **config 归属/作用域**：让上层只读 feature、不读底层 config；这是比本迭代大得多的模型变更。
4. **C 宏名唯一校验**：在加载期发现 `ctl.A_B` / `ctl.A.B` 这类碰撞。
